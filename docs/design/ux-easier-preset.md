# me 웹 UI — 최종 디자인 판정 (Senior Designer Final Judgment)

기준: 시각 토큰(app.css) 불변, 점+글자 라벨, 상태에만 색, 760px 분기, 다크/라이트, 44px 터치, a11y 0건, 호버 전용 정보 금지.

## 1. 주니어 결정별 판정

### 1.1 3탭 IA (대화 / 작업 / 상태) — **수정 수용 (accept with change)**

- 탭 5→3 통합, 승인 탭 폐지, 배지 단일화(작업 탭 `확인 필요` 하나)는 수용.
- **수정:** 주니어는 승인을 `작업` 탭 `확인 필요` 버킷으로 "완전 이관"한다고 했으나, 현재 `workItems()`는 위임 승인(`payload.messageId` 보유)만 포함한다(state.ts `isDelegationApproval`). **approval-policy가 올리는 비-위임 승인(수동 승인 요청)은 작업 항목이 아니라서 이 설계대로면 UI에서 증발한다.**
- 결정: `작업` 탭 최상단에 **"승인 요청" 섹션**(비-위임 승인 카드: 요약 + 위험 라벨 + 승인/거절)을 두고, 그 아래 기존 버킷(`확인 필요/진행 중/완료/실패`)을 유지. 위임 승인은 지금처럼 `확인 필요` 버킷 행으로. 배지 = 확인 필요 버킷 + 승인 요청 섹션의 합산 1개.
- 대화 목록의 "확인 필요" 점 표시는 유지(중복이 아니라 진입 신호). F1의 진짜 문제는 "어디서 처리하나"인데, 답은 "대화에서 바로, 모아서는 작업 탭에서"로 통일.

### 1.2 대화 안 인라인 승인 + 수락 — **수용 (accept)**

- 방향 정확. F2 해소의 핵심. 단, 승인 시점 카드와 결과 도착 카드의 정보를 구분한다(§2 사실 교정 참조).
- 승인 대기 카드(인라인): [상태점] + 한 줄 요약(a.summary) + 프로젝트 칩 + 도구(하네스) 선택 + [승인하고 시작] [거절] + `요청 내용` 접기(brief/criterion 원문).
- 결과 도착 카드(인라인): 이때는 diff가 존재하므로 `+N -N · 파일 N개` 통계 + [변경사항 적용] [거절] + [전체 diff ›] (작업 상세로). 수용.

### 1.3 용어 사전 — **대부분 수용, 2행 거절 (reject)**

수용: 하네스→실행 도구, `local.` 접두사 제거, 위임→작업 맡기기, 워커 보고→작업 결과, 적용·커밋→변경사항 적용, 지시 내용/완료 기준→요청 내용/완료 조건, `sealed`→검토 대기, `applied`→적용 완료.

**거절 ① — 위험 라벨 행:** 주니어의 `단순 조회 (안전) / 코드 수정 (보통) / 파일 삭제·외부 전송 (주의)`는 지어낸 매핑이다. approval-policy의 risk는 low/medium/high이고 요청 행위 종류 정보를 담지 않는다. 대신: 라벨은 `위험 낮음/보통/높음`을 유지하되 카드 첫 줄에 **a.summary(무엇을 하려는지)를 평이한 한국어 한 줄로** 노출해 "승인하면 무슨 일이 생기는지"를 답하게 한다(F9는 라벨 교체가 아니라 요약 전면 배치로 해소).

**거절 ② — 플러그인 표기 행:** 주니어의 `brgr=백그라운드 작업기, jev=기억 동기화, slang=요약기`는 사실 오류. 정확한 역할:

| 플러그인 | 실제 역할 | 상태 탭 표기 |
| :--- | :--- | :--- |
| gjc-head | 답변하는 헤드 | 대화 엔진 |
| jev | 직접 답할지, 맡길지 판단 | 응답 판단 |
| slang | 한국어 줄임말·은어 풀이 | 말 풀이 |
| summarize | 작업 지시서 작성 | 지시서 작성 |
| brgr | 워커 실행 | 워커 실행기 |
| approval-policy | 자동 승인 규칙(테스트 등) | 자동 승인 규칙 |

상태 탭 기본 화면에는 이 역할 표만 노출하고, 내부 id·pid·재시작·권한 등은 `[고급 진단]` 접기로 내린다(주니어의 escape hatch와 동일 결론, 이름만 정정).

### 1.4 작업 제목 출처 — **방향 수용, 필드 경로 정정 (accept with correction)**

- "사용자가 실제로 입력한 최초 메시지를 제목으로"는 정답(F4 해소).
- **정정:** 클라이언트 `Task` 타입에 `origin.messageId`는 **없다**(api.ts:33-47). discovery의 주장이 코드와 다르다. 실제 경로: `message.taskId`(chat.tsx:254에서 이미 사용 중)를 역참조해 위임 메시지를 찾고, **같은 스레드에서 그 직전의 사용자 메시지 텍스트**를 제목으로 쓴다. 못 찾으면 기존 `task.objective` 첫 줄로 폴백.
- 40자 말줄임 규칙, 영문 brief는 상세 `요청 내용` 접기로 이동 — 수용.

### 1.5 경로 표시 규칙 — **수정 수용 (accept with change)**

- 저장소명 칩(`📁 repo-name`) 표기, 임시 경로→`임시 프로젝트` — 수용. 단 임시 접미사 `(um4yFF)`는 노이즈이므로 제거. repoName() 헬퍼가 이미 있으니 재사용.
- **수정:** "호버 시 title 툴팁으로 전체 경로"는 **AGENTS 규칙(호버 전용 정보 금지) 위반**이자 모바일에서 접근 불가. 전체 경로는 작업 상세의 `상세 정보` 접기 안에 텍스트로 표기 + 복사 버튼. 칩 자체는 링크/버튼으로 만들지 않는다(정보는 칩에 완결).

### 1.6 기타 판정 (일괄)

- 작업 상세 리오더(결과 요약+diff 최상단 → 액션 바 → 메타 접기), 적용 후 `diff 새로고침` 제거(review.tsx:102) — **수용**. 진행 중(review 가능 상태 전)에는 "새로고침"이 아니라 diff가 자동 로드되므로 버튼 자체를 조건부로: `sealed/accepted/apply-failed`에서만, 라벨은 `다시 불러오기`.
- 상태 탭 "모든 시스템 정상" 요약 카드 + 프로젝트 섹션 통합 + 플러그인 원시 목록 숨김 — **수용**.
- 모바일 홈(F5): 주니어가 "최근 대화 자동 오픈 또는 고정 composer" 둘을 병기했는데 하나로 결정한다 — **대화 목록 하단에 입력창 고정(새 대화 시작), 기존 스레드 탭 시 해당 대화에서 이어쓰기**. 자동 오픈은 목록 개요를 빼앗아 거부.

## 2. 사실 교정 (주니어가 틀린 부분)

1. **승인 시점에 diff/파일 수는 존재하지 않는다.** 승인은 워커 실행 전에 일어난다. approval payload에는 `summary, brief, criterion, project, harness, harnesses, risk`뿐이다(approvals.tsx:34-67). 주니어 §3.3의 "`3개 파일 변경 예정 · 저장소: repoName`" 표기는 **불가능**. 교정: 승인 카드 첫 줄은 "무엇을·어디서·어떤 도구로" — 즉 `a.summary` + 프로젝트 칩 + 선택된 도구명 + 위험 라벨. 파일 수 통계는 결과 도착(`sealed`) 이후에만 보인다.
2. **비-위임 승인의 존재.** approval-policy가 올리는 수동 승인(테스트 외 명령 등)은 위임이 아니며 messageId가 없어 작업 항목으로 파생되지 않는다. 승인 탭 폐지 시 별도 수용처가 필요(§1.1).
3. **플러그인 역할 오기재.** jev는 "기억 동기화"가 아니라 응답 판단, slang은 "요약기"가 아니라 줄임말 풀이(§1.3 표).
4. **`task.origin.messageId` 부재.** 제목 소스는 `message.taskId` 역참조 + 같은 스레드 직전 사용자 메시지(§1.4).
5. **호버 툴팁 제안은 규칙 위반.** 호버 전용 정보 금지(§1.5).

      - 승인 카드 인라인화로 위험 고지 약화 우려 → 요약+위험 라벨을 카드 첫 줄 고정, 접기 불가

## 4. 최종 용어표 & 인수 기준

### 4.1 최종 용어표

| 현재 | 최종 | 사용처 |
| :--- | :--- | :--- |
| 하네스 / `local.claude-code` | 실행 도구 / Claude Code · Codex (`local.` 제거) | 승인 카드, 작업 상세, 행 |
| 위임 | 작업 맡기기 (명사형은 "맡긴 작업") | 대화 카드, 알림 |
| 워커 보고 | 작업 결과 | 상세 섹션 제목 |
| 적용·커밋됨 / accept | 변경사항 적용 / 적용 완료 | 리뷰 바, 상태 라벨 |
| diff 새로고침 | 다시 불러오기 (검토 가능 상태에서만) | 리뷰 바 |
| 지시 내용 / 완료 기준 | 요청 내용 / 완료 조건 | 승인 카드·상세 접기 |
| 위험 낮음/보통/높음 | 유지 + 카드 첫 줄에 요약 상시 노출 | 승인 카드 |
| `sealed` / `applied` / `needs` | 검토 대기 / 적용 완료 / 확인 필요 | 상태 라벨 |
| 플러그인 id (brgr 등) | 역할 표기: 워커 실행기·응답 판단·말 풀이·지시서 작성·대화 엔진·자동 승인 규칙 | 상태 탭 |
| 절대 경로 | 📁 repo-name 칩 (전체 경로는 상세 접기+복사) | 전 화면 |
| 영문 brief (제목) | 사용자 원문 메시지 40자 말줄임 | 작업 행·상세 헤더 |

### 4.2 인수 기준 (스크린샷 검증 가능)

1. **탭 3개:** 네비게이션에 `대화·작업·상태`만 보이고, `승인·프로젝트` 탭이 없다. 배지는 작업 탭 숫자 하나뿐이다.
2. **인라인 승인:** 승인 대기 위임이 있는 대화 스크린샷에서 카드 안에 도구 선택과 [승인하고 시작]이 보이고, 승인 후 같은 화면에서 `진행 중`으로 바뀐다(URL이 #/chat 그대로).
3. **승인 요청 섹션:** 비-위임 승인(approval-policy 수동 건)이 있을 때 작업 탭 최상단 `승인 요청` 섹션에 요약·위험 라벨·승인/거절이 보인다.
4. **인라인 수락:** 완료된 위임의 대화 카드에 `+N -N` 통계와 [변경사항 적용]이 보이고, 클릭 후 카드가 `적용 완료`로 바뀐다.
5. **한글 제목:** 작업 목록 행의 제목이 사용자의 한글 질의(40자 말줄임)로 표시되고, 영문 brief는 행 어디에도 없다.
6. **상세 리오더:** 작업 상세 스크린샷 첫 화면에 메타 표가 없고, `작업 결과`와 파일 diff가 먼저 보인다. 하단 바에 [변경사항 적용][거절]만 있다(적용 완료 상태에서 `diff 새로고침` 없음).
7. **경로 정제:** 전 화면에서 30자 이상 절대 경로가 0건이고 프로젝트 칩만 보인다. 전체 경로는 상세 `상세 정보` 접기를 펼쳤을 때만 텍스트+복사 버튼으로 보인다(호버 없이).
8. **상태 탭 요약:** 상태 탭 첫 화면에 정상/점검 요약 카드와 기기 상태가 보이고, 플러그인 원시 id 목록은 `고급 진단` 접기를 펼치기 전엔 보이지 않는다.
9. **회귀 게이트:** `bun run a11y` 0건, `bun run shots` 가로 넘침 0, 44px 터치 유지.

## 5. 대표 미리보기 화면 & exemplar 구현 순서

### 5.1 승인 전 미리보기 1개

**모바일 390px 대화 스레드 — 승인 대기 위임 카드 인라인 상태.**

이 한 화면이 테제 전부를 증명한다: 메신저 맥락 유지 + 도구 선택 + 위험/요약 고지 + 탭 이탈 없는 승인. (결과 수락 카드는 동일 카드의 상태 변주라 같은 레이아웃으로 검증 가능.)

### 5.2 Exemplar 구현 순서

1. **대화방 인라인 위임 카드** — 승인 대기(도구 선택+승인/거절) + 결과 도착(통계+적용/거절) 두 상태. chat.tsx `DelegationLine` 교체. 라우트 이동 제거가 여기서 검증됨.
2. **작업 탭 통합** — 승인 요청 섹션(비-위임) + 확인 필요 버킷 + 배지 단일화, 승인 탭 제거와 라우트 리다이렉트.
3. **작업 상세 리오더** — 결과 우선 배치, 메타 접기, 리뷰 바 정리.
4. **제목·경로 규칙** — message.taskId 역참조 제목 + repoName 칩 + 경로 접기 (전 화면 공통 헬퍼라 늦게 묶어도 충돌 없음).
5. **상태 탭 통합** — 요약 카드, 프로젝트 섹션 이관, 플러그인 고급 진단 접기, 프로젝트 탭 제거.
6. **게이트** — a11y + shots 회귀, §4.2 전 항목 스크린샷 대조.


## 부록: Codex 앱 조사 반영 (2026-10-11)

출처: [codex-app-ux.md](../research/codex-app-ux.md) (GJC · gpt-6.1-sol autoresearch). 공식 문서 6곳이 열리는지, 설치 앱의 식별자·버전, 코드 관찰 3건(`state.ts` toneOf·threadTone, `chat.tsx` 인라인 카드)을 직접 다시 확인했다. 프리셋 방향은 바꾸지 않고 아래만 더한다.

1. 승인 카드에 시작 효과를 한 줄로 적는다: "승인하면 선택한 실행 도구가 이 프로젝트에서 작업을 시작해요". payload에 없는 행동은 지어내지 않는다.
2. 결과 카드의 `변경사항 적용` 옆에 "이 작업의 변경사항을 적용하고 커밋해요"를 늘 보여준다. `accepted`는 `적용 중`, `applied`만 `적용 완료`다. 지금은 `toneOf`가 둘 다 done으로 친다. commitSha가 있으면 보여준다.
3. 결과 카드에 "수정 요청은 아래 메시지로 보내 주세요"를 넣는다. 라인 댓글 API는 만들지 않는다.
4. 대화 목록에서 실패를 숨기지 않는다. 지금은 `threadTone`이 failed를 none으로 바꾼다. 거절·취소만 숨긴다.
5. 상태 탭 점검 요약에 `마지막 확인` 시각을 넣고, 웹 연결 정상과 워커 기기 정상을 따로 보여준다.
6. 빈 상태 문구: 대화 목록 "무엇을 도와드릴까요? · 아래에 메시지를 보내 새 대화를 시작하세요", 작업 "지금 확인할 일이 없어요".

하지 않을 것: Cloud·worktree 선택기, 자동 승인 모드, hunk stage/revert·Push·PR 버튼, 일괄 읽음 처리.
